# dsh-why · 产品愿景（Vision）

> 状态：**v1.0 · 2026-09-10** · 首次成文 · 站点与品牌：**dsh-why.com** · 仓库：[dsh-why](https://github.com/ice5kysl/dsh-why)
> 文档地图：VISION（为什么）→ [README](../README.zh-CN.md)（用法 / CLI 参考 / 工作原理）· 姊妹项目：[dsh-insights](https://dsh-insights.com)（选型）· dsh-insights-kit（体检）

## 一句话愿景

**让每一次 dsh 红屏（`Failed to load plugins`）都能在 30 秒内变成一份可执行的修法清单：`npx dsh-why` 说清装了什么、什么崩了、为什么、怎么办——只读、零依赖、断网可用，且诚实到肯承认自己的盲区。**

DSH 的哲学是 "Everything is a Plugin"；dsh-why 的回答是：**Every crash deserves an honest explanation —— 修法要么给出，要么明说不知道，绝不编造确定性。**

## 我们解决的问题

dsh 的 web shell 不允许插件 client bundle 任意 `require()` npm 包——require 只对照**烘焙进 shell 构建产物的模块表**解析。官方演进（rc 移除 / 新增模块）持续制造「这版能跑、那版崩」的兼容断裂，而红屏报错文本对用户是零行动指引的：

- 用户不知道**是哪个插件**、**缺哪个模块**、**谁的锅**（插件作者该加守卫？还是自己升/降 dsh 就行？）；
- 用户的第一反应是搜索或粘贴给 AI——缺一个**本地的、即刻的、可信的**答案；
- 报错可能来自一台**插件根本没装成**的机器，诊断不能依赖「本机装齐」这一前提。

## 在生态中的位置（三件套，同一口径）

| 工具 | 时机 | 回答的问题 |
|---|---|---|
| [dsh-insights.com](https://dsh-insights.com) | 选型时（事前） | 这个插件信得过吗（健康分 / 实测兼容矩阵） |
| dsh-insights-kit | 安装后（事前体检） | 我当前的插件组合健康吗 |
| **dsh-why** | **崩溃后（事后）** | **为什么挂了、怎么修** |

线上矩阵与本地 CLI 跑的是**同一套 guard-aware 扫描器代码**：本地结论与生态数据同口径，互相校核而非各说各话。

## 我们是什么 / 不是什么

**是**：只读的诊断 CLI（`--json` / `--error` / `--prompt`）+ 浏览器粘贴红屏的诊断页（dsh-why.com），由一套规则库（R1 模块表缺失 / R2 engines.dsh / R3 新版可升 / R4·R5 生态对照 / R6 profile 完整性）、报错解析器和修法输出（issue 模板 / AI fix prompt / CI 退出码）构成。

**不是**（边界，决策过滤器）：

- ❌ 永远不修改用户的任何文件——只告诉你怎么修，不替你修（**只读是信任的根基**）。
- ❌ 不是安装器 / 卸载器 / 插件管理器 / 第 N 个插件目录。
- ❌ 不做遥测——在线模式只发三类 GET（dsh-insights 数据、npm registry `latest`），机器信息永不上传。
- ❌ 不猜——判定不了就输出「无法判定」警告并给出核实方法，绝不把自己的盲区变成红牌。
- ❌ 不做通用「dsh doctor」——聚焦失败诊断这一件事，做到可信。

## 用户与主任务

| 用户 | 主任务 |
|---|---|
| 插件使用者 | 红屏后 30 秒拿到修法（升 / 降 / 移除 / 提 issue），拿到生态佐证（「你不是唯一踩坑的」） |
| AI agent / CI | `--json` 喂模型、退出码 1 当门禁、`--prompt` 直接驱动修复 |
| 插件作者 | 收到预填好的 issue 模板；事前自检（守卫感知扫描、engines.dsh 诚实声明） |
| dsh-insights | 线上矩阵与本地诊断互为印证，共用扫描器与数据快照 |

## 产品支柱

1. **P1 诚实的判定**：四态判定（可解析 / 条件可解析 / 缺失 / 无法判定）镜像加载器自身的解析序；守卫感知（`try/catch` 兜住的缺失是备注不是崩溃）；每个模块的沿革（何时移除 / 加入 / 从未提供）**从已发布 shell 历史推导**，不硬编码断裂点。
2. **P2 零门槛触达**：`npx` 免安装、**零 npm 依赖**、Node ≥ 18、断网回退包内快照、中英双语按 locale 自适应——任何人任何机器上「跑一下」的摩擦为零。
3. **P3 报错即入口**：粘贴红屏文本（`--error` / 管道 / 网页）即可诊断，**即使本机没装该插件**；不认识的报错诚实说明并列出已支持模式。
4. **P4 修法可执行**：每条结论带修法（升 / 降 / 移除 / 提 issue）、可复制的 GitHub issue 模板、可粘给 AI agent 的 fix prompt、可当 CI 门禁的退出码——诊断的终点是行动，不是描述。
5. **P5 永远能跑**：诊断工具自己永不崩（内部错误 = exit 2 = 请提 issue）；优雅降级而非编造；快照来源（线上 / 包内）永远标明——**模型本身就是结论的一部分**。

## 指导原则

只读是信任的根基 · 诊断工具自己永不崩 · **永远不比自己的输入更自信**（无法判定 ≠ 缺失）· 从已发布事实推导，不靠猜 · 断网不是二等公民 · 零依赖是分发承诺，不是实现洁癖 · 一套代码三个面（CLI / JSON / web），口径只有一份。

## 成功指标

- **北极星**：红屏求助场景里「先跑 `npx dsh-why`」成为生态的肌肉记忆——被用户回答、被插件作者写进 README、被官方文档或 issue 指引引用。
- 覆盖：已知加载器报错模式的解析覆盖率；R1 判定对真实崩溃的命中率与误报率（守卫/条件态不翻红）。
- 采纳：插件作者 CI 采用退出码门禁；issue 模板出现在真实 issue 里；`--prompt` 被 agent 实际消费并修复成功。
- 供给：shell 模块表快照与案例库的刷新滞后；断网模式与在线模式结论的一致性。

## 止损 / Kill criteria

- dsh 官方内置等价诊断（如 `dsh doctor`）且口径覆盖我们 → 贡献 upstream / 被收编（预留 exit）。
- 加载器模块表机制根本变化，且无法从新的已发布事实推导 → 归档并在 README 指向官方工具。
- 快照/规则维护成本持续超过价值 → 收缩为纯报错解析器（仍只读、仍零依赖）。

## 开放问题

- O1 `--package <dir>` 插件作者自检模式（README 已预告 "welcome PR"）：优先级与形态（本地目录扫描 vs CI action）。
- O2 报错模式的收录管道：新报错如何从 issue / 案例库回流到 errparse 的已知模式。
- O3 与 dsh-insights 的数据联动节奏：`shell-seeds.json` / `fixes.json` 快照的同步策略与滞后容忍度。
- O4 agent 原生入口（MCP server 等）是否值得做——或维持「CLI + `--json` + `--prompt`」即足以被任何 agent 消费。
