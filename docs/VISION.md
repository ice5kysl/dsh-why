# dsh-why · 产品愿景（Vision）

> 状态：**v1.1 · 2026-09-10** · 站点与品牌：**dsh-why.com** · 仓库：[dsh-why](https://github.com/ice5kysl/dsh-why)
> 文档地图：VISION（为什么）→ [README](../README.zh-CN.md)（用法 / CLI 参考 / 工作原理）· 姊妹项目：[dsh-insights](https://dsh-insights.com)（选型）· dsh-insights-kit（体检）

## 一句话愿景

dsh 出问题时的「为什么」：**本地失败诊断 + 恢复计划 + 生态已知问题对照**——让每一次 dsh 红屏（`Failed to load plugins`）都能在 30 秒内变成一份可执行的修法清单。只读、零依赖、断网可用，且诚实到肯承认自己的盲区。

DSH 的哲学是 "Everything is a Plugin"；dsh-why 的回答是：**Every crash deserves an honest explanation —— 修法要么给出，要么明说不知道，绝不编造确定性。**

## 需求证据与竞争格局

- **incumbent 证明需求真实**：`@huichangzz/dsh-postmortem` 基线周下载 230-350，被推荐周冲到 **1,189**——分发事件能放大 4-5 倍。零营销、纯需求驱动。
- **两层不重叠，各守主场**：它是**会话运行复盘**（agent 跑挂了：工具失败/重试空转），我们是**加载崩溃 + 环境兼容**（装不上/起不来/升不升）。
- **护城河**：接 [dsh-insights](https://dsh-insights.com) 的实测兼容矩阵（compat-observed）——诊断输出不只是「这个 require 缺了」，而是「这个错在全生态出现过 N 次、是某插件 × 某 shell 版本的已知不兼容、已知修法是 X」。**别人抄不走生态数据。**
- 官方 `.agents/notes/` 在诊断/复盘领域零命中，吸收风险极低。

## 形态决策：CLI 是产品，插件壳是渠道

**诊断工具必须在 dsh 挂掉时也能用。** web 面板在「插件加载失败」红屏时恰恰打不开——最需要诊断的时刻，插件形态的诊断工具不可用。所以：

- **主入口是 CLI**：`npx dsh-why` 零安装，危机时刻没有「要不要装」的心理门槛（incumbent 要 npm install + 手工编辑 `cordis.patch.yml` 两步）。
- **CLI 是产品，插件壳是渠道**：v0.2.x 可选 cordis 插件薄壳（无 UI），注册 `dsh why` 命令、被观测站收录/进场景推荐——壳只为分发存在。
- **web 粘贴页是第三入口**（dsh-why.com）：不依赖本机 dsh，服务于「手里攥着报错文本」的时刻（含搜索引擎与 AI 助手的落地页），不与 CLI-first 冲突。

## 在生态中的位置与数据飞轮

| 资产 | 时机 | 回答的问题 |
|---|---|---|
| [dsh-insights.com](https://dsh-insights.com) | 选型时（事前） | 这个插件信得过吗（健康分 / 实测兼容矩阵） |
| dsh-insights-kit | 安装后（事前体检） | 我当前的插件组合健康吗 |
| **dsh-why** | **崩溃后（事后）** | **为什么挂了、怎么修** |

**飞轮**：compat-observed 是 dsh-why 的数据源；未来的 `--share` opt-in 上报（脱敏白名单）反哺崩溃原因库。单品类天花板不高（incumbent 基线 ~300/周）——对策是双受众（用户排障 + 作者 CI 自测）+ 观测站「数据采集终端」的战略位，**战略价值大于下载量**。线上矩阵与本地 CLI 跑同一套 guard-aware 扫描器，口径只有一份。

## 我们是什么 / 不是什么

**是**：只读的诊断 CLI（`--json` / `--error` / `--prompt`）+ 浏览器粘贴红屏的诊断页，由规则库（R1 模块表缺失 / R2 engines.dsh / R3 新版可升 / R4·R5 生态对照 / R6 profile 完整性）、报错解析器和修法输出（issue 模板 / AI fix prompt / CI 退出码）构成。

**不是**（边界，决策过滤器）：

- ❌ **不做自动修复**——只给指引不动手，永远不修改用户的任何文件（只读是信任的根基）。
- ❌ **模型不参与诊断**——保持零模型依赖；若未来加模型层，纪律照抄 postmortem：只解释已检测到的故障、不控制执行、输出无效即丢弃回退确定性报告。
- ❌ **不做会话运行复盘**——那是 dsh-postmortem 的主场，两层不重叠。
- ❌ 不是安装器 / 卸载器 / 插件管理器 / 第 N 个插件目录。
- ❌ 不做遥测——在线模式只发三类 GET（dsh-insights 数据、npm registry `latest`）；`--share` 上报必须是 opt-in 且脱敏。
- ❌ 不猜——判定不了就输出「无法判定」警告并给出核实方法，绝不把自己的盲区变成红牌。

## 用户与主任务（双受众）

| 用户 | 主任务 |
|---|---|
| 插件使用者 | 红屏后 30 秒拿到修法（升 / 降 / 移除 / 提 issue）与生态佐证（「你不是唯一踩坑的」） |
| 插件作者 | **CI pre-publish 自检**（守卫感知扫描、engines.dsh 诚实声明、退出码门禁）；收到预填好的 issue 模板 |
| AI agent / CI | `--json` 喂模型、退出码 1 当门禁、`--prompt` 直接驱动修复 |
| dsh-insights | 线上矩阵与本地诊断互为印证；未来互为数据源（飞轮） |

## 产品支柱

1. **P1 诚实的判定**：四态判定（可解析 / 条件可解析 / 缺失 / 无法判定）镜像加载器自身的解析序；守卫感知（`try/catch` 兜住的缺失是备注不是崩溃）；每个模块的沿革（何时移除 / 加入 / 从未提供）**从已发布 shell 历史推导**，不硬编码断裂点。
2. **P2 零门槛触达**：`npx` 免安装、**零 npm 依赖**、Node ≥ 18、断网回退包内快照、中英双语——任何人任何机器上「跑一下」的摩擦为零。
3. **P3 报错即入口**：粘贴红屏文本（`--error` / 管道 / 网页）即可诊断，**即使本机没装该插件**；不认识的报错诚实说明并列出已支持模式。
4. **P4 修法可执行**：每条结论带修法、可复制的 issue 模板、可粘给 AI agent 的 fix prompt、可当 CI 门禁的退出码——诊断的终点是行动，不是描述。
5. **P5 永远能跑**：诊断工具自己永不崩（内部错误 = exit 2 = 请提 issue）；优雅降级而非编造；快照来源（线上 / 包内）永远标明——模型本身就是结论的一部分。

## 分发：路标系统（比工具本身更决定成败）

诊断工具没有「日常曝光」场景，发现只能发生在**问题现场**。用户出问题时只有三条动线，逐条埋点——「什么时间用」不靠用户记忆，现场有路标，用户照抄即可，甚至不需要记住 dsh-why 这个名字：

1. **现场（最强渠道）**：insights-kit 体检 tab 的红标 / 升级横幅 / 「不建议安装」tooltip 统一带「跑 `npx dsh-why`」。kit 装机量 = dsh-why 发现率，两产品互为漏斗。
2. **搜索**：README 用真实错误字符串写（不用营销语言）——`Failed to load plugins`、`missed the module table`、`bundle script failed` 每个报错一节，用户粘贴报错搜索时命中我们。
3. **AI 助手**：用户粘贴报错问 LLM 是主流排障方式——llms.txt + 错误专题页保持 LLM 可读，让「dsh 插件加载失败怎么办」的答案源头是我们的站。

## 指导原则

CLI 是产品，插件壳是渠道 · 只读是信任的根基 · 诊断工具自己永不崩 · **永远不比自己的输入更自信**（无法判定 ≠ 缺失）· 从已发布事实推导，不靠猜 · 断网不是二等公民 · 零依赖是分发承诺 · 一套代码三个面（CLI / JSON / web），口径只有一份。

## 成功指标

- **北极星**：问题现场的路标密度 + 社区标准答案——kit 红标带出的命令、红屏求助里「先跑 `npx dsh-why`」的回答、作者 README 与官方文档的引用。
- **量化**：首月周下载 ≥ **300**（追平 incumbent 基线 230-350/周；其峰值周证明分发事件能放大 4-5 倍——我们自带路标系统）。
- **采纳**：被 awesome 目录收录；插件作者 CI 采用退出码门禁；issue 模板出现在真实 issue 里；`--prompt` 被 agent 实际消费。
- **供给**：shell 模块表快照与案例库的刷新滞后；断网模式与在线模式结论的一致性。

## 止损 / Kill criteria

- dsh 官方下场做诊断 → 差异化收缩到「生态数据对照」（insights 矩阵仍是独家），或贡献 upstream / 被收编（预留 exit）。
- 加载器模块表机制根本变化，且无法从新的已发布事实推导 → 归档并在 README 指向官方工具。
- 快照/规则维护成本持续超过价值 → 收缩为纯报错解析器（仍只读、仍零依赖）。

## 开放问题

- O1 `--package <dir>` 插件作者自检模式（README 已预告 "welcome PR"）：优先级与形态（本地目录扫描 vs CI action）。
- O2 报错模式的收录管道：新报错如何从 issue / 案例库回流到 errparse 的已知模式（第一步先做「未识别报错 → 预填 issue 链接」的低成本出口）。
- O3 与 dsh-insights 的数据联动节奏：`shell-seeds.json` / `fixes.json` 快照的同步策略与滞后容忍度。
- O4 cordis 插件薄壳的时机（v0.2.x，注册 `dsh why` 命令）——渠道价值 vs 维护成本。
- O5 `--share` opt-in 上报：需服务端收集端点，**独立决策**；脱敏照抄 postmortem 白名单（轮次号/工具名/不透明 ID/错误码，绝不含用户消息与文件内容）。
- O6 agent 原生入口（MCP 等）——倾向搁置，「CLI + `--json` + `--prompt`」已能被任何 agent 消费。
